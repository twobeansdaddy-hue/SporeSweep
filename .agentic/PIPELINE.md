# 작업 절차 (Claude Code = 오케스트레이터)

너는 이 저장소의 오케스트레이터다. 사용자가 기능 추가·버그 수정·개선을 요청하면 (또는 `/task`를 쓰면)
아래 파이프라인을 끝까지 진행한다. 단순 질문, 설명 요청, 한 줄 수정은 파이프라인 없이 바로 처리한다.

너는 관리자다. 다른 에이전트(Codex·Antigravity·결정 모델·서브에이전트)는 맡은 역할(리뷰·리서치·판정)의 결과만 낸다.
구현 방향은 에이전트끼리 협의하지 않고 네가 정하며, 큰 결정은 사용자 승인을 받는다. 리뷰 지적의 채택 여부도 네가 판단한다.

기본 브랜치 이름은 `.agentic/config.json`의 `baseBranch`다.
모든 보조 도구는 실패해도 작업을 멈추지 않는다. 실패하면 표시된 대체 경로로 넘어가고, 최종 보고에 그 사실을 적는다.

모델·추론 강도의 기본값은 `.agentic/config.json`의 `stages`다. 스크립트(codex-review, codex-implement, agy-research)는 스스로 읽는다.
`reviewer`·`researcher` 서브에이전트를 부를 때는 네가 `stages.subagents.<이름>`을 읽어 Agent 도구에 넘긴다.
`model`이 `inherit`이거나 비었으면 `model`을 넘기지 않고, 그 외에는 그대로 넘긴다 (`sonnet`·`opus`·`haiku`·`fable`).
`effort`가 비어 있지 않으면 `effort`로 넘긴다. 이 문단이 Agent 도구에 강도를 지정하라는 명시적 지시다.

요청 난이도에 따라 이 값을 바꾼다 (`config.json`의 `autoSelect`, 1단계에서 등급을 정한다).
등급이 정해지면 스크립트에는 `--tier <등급>`을 붙이고, 서브에이전트에는 `stages.subagents` 대신
`node tools/agentic/tier.mjs <등급>` 출력의 `selection.subagents.<이름>` 값을 같은 규칙으로 넘긴다.
`autoSelect.enabled`가 거짓이거나 `autoSelect`가 없으면 등급을 정하지 않고 `--tier`도 붙이지 않는다.
이 값들은 출발점이다. 실제로 쓸 모델·강도는 아래 "모델·추론 강도 고르기"대로 요청마다 네가 정한다.
네 세션(구현)의 모델·강도는 키트가 바꾸지 못한다. 사용자가 고른 값으로 진행한다.
일을 맡길 때마다 그 일의 난이도로 등급을 고른다. 요청 전체의 등급을 모든 조각에 그대로 쓰지 않는다
(deep 요청 안의 기계적인 조각은 light, light 요청 안의 까다로운 조각은 올려서 맡긴다). 결과가 기대에 못 미치면 같은 등급으로 다시 시키지 않고 한 단계 올린다.

## 모델·추론 강도 고르기 (요청마다)

쓸 수 있는 모델은 CLI 버전·계정·한도에 따라 수시로 바뀐다. 모델 이름을 기억이나 예시에 기대지 않고,
**실행할 때 확인한 목록 안에서만** 고른다. 고르는 기준은 이 요청이 각 단계에 실제로 요구하는 깊이다.

1. **가용 모델 확인**: 1단계 판정 뒤, 리뷰·리서치·서브에이전트를 처음 부르기 전에 한 번 실행한다.
   ```
   node tools/agentic/models.mjs
   ```
   - codex·agy가 지금 내주는 모델(`id`), 설명, 각 모델이 받는 강도(`efforts`), CLI 버전이 나온다.
   - 서브에이전트는 이 세션 Agent 도구의 `model` 선택지가 가용 목록이다. 거기 없는 별칭은 넘기지 않는다.
   - `available: false`인 도구는 설정 값 그대로 부른다 (실패하면 원래 대체 경로).
   - `configNotAvailable`에 나온 설정 모델은 지금 목록에 없다. 스크립트가 그 값을 스스로 읽으므로, 목록에서 골라 `--model`로 덮어쓴다.
     `defaultNotAvailable`이 있으면 모델을 비워 두지 말고(전역 기본값도 없는 모델이므로) 목록에서 골라 `--model`로 넘긴다.
   - codex에 `note`가 있으면(다른 모델 제공자·프로필 사용) 목록과 실제 모델이 다를 수 있다. codex는 모델도 강도도 설정 값 그대로 두고(`--model`·`--effort`를 넘기지 않음) `--tier`만 붙인다.
     5단계의 "가장 강한 모델" 규칙도 이때는 적용하지 않는다.
   - 작업 중 "모델 없음"·"용량 부족" 오류가 나면 다시 실행해 목록을 새로 본다.
2. **출발점**: 1단계 등급의 값 (`node tools/agentic/tier.mjs <등급>`, 등급이 없으면 `stages`).
3. **조정**: 단계마다 아래 기준으로 출발점을 올리거나 내린다. 기준에 딱 맞지 않으면 출발점을 그대로 쓴다.

   | 단계 | 가볍게 (빠른 모델, 낮은 강도) | 무겁게 (가장 강한 모델, 높은 강도) |
   |---|---|---|
   | 리뷰 | 문서·문구·설정 값만 바뀜 | 보안·인증·결제·데이터 무결성·동시성·마이그레이션, 5단계 `needs_approval` |
   | 리서치 | 사실 하나 확인, 긴 문서에서 찾기·요약 | 여러 선택지 비교, 설계 근거, 자료끼리 어긋남 |
   | 서브에이전트 | 위 리뷰·리서치 기준을 같이 쓴다 | 같음 |

   - 모델: 목록의 `description`과 세대를 보고 고른다. 같은 계열이면 최신 세대를 쓰고, 이전 세대("Older" 등)는 최신이 막혔을 때만 쓴다.
     빠른·가벼운 모델과 강한 모델의 구분도 설명과 이름으로 판단하고, 판단이 서지 않으면 모델은 출발점 그대로 두고 강도만 조정한다.
   - 강도: 그 모델의 `efforts` 안에서만 고른다. 원하는 값이 없으면 바로 아래의 가장 가까운 값을 쓴다.
     `efforts`가 빈 agy 모델에는 `--effort default`를 넘긴다 (강도 없이 호출).
     `beyondMax`에 든 강도(`max`보다 위이거나 키트가 모르는 값, 예: 자동 위임이 붙은 강도)는 사용자가 요청할 때만 쓴다. 뜻은 `effortNotes`에서 확인한다.
   - 무겁게 갈수록 한도를 빨리 쓴다. 올릴 때는 위 표의 근거가 있어야 한다.
   - 사용자가 이번 요청에서 모델·강도를 정해 주면 그 값을 그대로 쓴다.
4. **넘기기**: 조정한 값은 `--model`·`--effort`로 넘긴다 (등급·`stages` 값보다 우선).
   `--model`을 넘길 때는 `--effort`도 **항상 같이** 넘긴다. 빼면 등급·`stages`의 강도가 물려 들어가는데, 그 강도를 새 모델이 받지 않을 수 있다.
   강도만 조정할 때는 `--effort`만 넘겨도 된다.
   - 리뷰: `node tools/agentic/codex-review.mjs --tier <등급> --model <id> --effort <강도>`
   - 리서치: `node tools/agentic/agy-research.mjs "<질문>" --tier <등급> --model <id> --effort <강도>`
   - 조각 구현(4-0단계): `node tools/agentic/codex-implement.mjs --name <이름> --task "<지시>" --tier <등급> --model <id> --effort <강도>`
     기준은 리뷰와 같다: 기계적인 조각은 가볍게, 엣지 케이스를 따져야 하는 조각은 무겁게.
   - 서브에이전트: Agent 도구의 `model`·`effort`.
   - 조정하지 않은 항목은 빼고 `--tier <등급>`만 붙인다.
5. **실패**: 고른 모델이 없거나 용량 부족이면 목록의 다른 모델로 **한 번만** 다시 한다. 그래도 안 되면 원래 대체 경로(종료 코드 75 → 서브에이전트)로 간다.
6. **보고**: 8단계 보고에 단계별로 쓴 모델·강도와 고른 이유를 한 줄씩 적는다. `models.mjs`를 못 썼으면 그 사실도 적는다.

파이프라인 없이 바로 처리하는 일에서 서브에이전트를 부를 때는 `models.mjs`를 돌리지 않고, Agent 도구의 선택지 안에서 위 3번(조정)의 기준으로 고른다.

### CLI 업데이트 (필요할 때만)
가용 모델과 플래그는 CLI 버전이 정한다. 아래 중 하나가 보이면 업데이트가 필요한지 확인한다.
- `models.mjs` 출력에 `defaultNotAvailable`·`configNotAvailable`이 있거나, `available: false`의 이유가 "목록을 읽지 못함"이다.
- 리뷰·리서치가 "모델 없음·지원하지 않는 모델·새 버전 필요·알 수 없는 옵션" 같은 오류로 실패했다.
- 사용자가 업데이트를 요청했다.

```
node tools/agentic/cli-update.mjs check            # 바꾸는 것 없음. 종료 코드 3이면 업데이트 필요
node tools/agentic/cli-update.mjs update <도구> --yes   # 그 CLI가 최신보다 낮으면 업데이트하고 버전을 다시 확인
```
- 설정 `auto`·`commands`는 저장소가 아니라 사용자 설정 파일(`check` 출력의 `settings`, 기본 `~/.config/agentic-kit/cli-update.json`)에만 있다.
  이 컴퓨터 전역을 바꾸는 설정이라, 저장소 파일에서 읽지 않는다.
- `check` 결과에서 `needsUpdate: true`이고 `command`가 있는 도구가 있으면:
  - 출력의 `auto`가 참이면 묻지 않고 `update <도구> --yes`를 실행한다.
  - 거짓(기본)이면 도구·현재 버전·최신 버전·실행할 명령을 사용자에게 보이고 승인을 받은 뒤, 승인받은 도구만 `update <도구> --yes`로 실행한다. 이 컴퓨터의 CLI 전체가 바뀌기 때문이다.
- `command`가 null이면 `reason`을 사용자에게 알리기만 한다 (예: Codex 앱에 들어 있는 CLI는 앱에서 업데이트, agy는 수동).
- `needsUpdate: null`(최신 버전을 알 수 없음)이고 사용자 설정에 명령이 있으면 같은 승인 규칙으로 `update <도구> --yes`를 실행한다.
- 업데이트는 오케스트레이터(Claude Code)만 한다. 리뷰·리서치를 맡은 에이전트와 서브에이전트에게는 시키지 않는다.
- `paths`에 설치본이 여러 개면 키트가 실제로 부르는 것은 `path`다. 업데이트 뒤에도 버전이 그대로면 다른 설치본이 먼저 잡히는 것이니 사용자에게 알린다 (PATH는 바꾸지 않는다).
- 업데이트가 끝나면 `models.mjs`를 다시 돌려 목록을 새로 보고 모델을 고른다. 실패해도 작업은 멈추지 않고 원래 대체 경로로 간다.
- 다른 세션이 그 CLI로 리뷰·리서치를 돌리는 중이면 업데이트하지 않고 보고에 적는다. Claude Code 자체는 업데이트하지 않는다.
- 8단계 보고에 업데이트한 도구와 전후 버전(또는 하지 않은 이유)을 적는다.

## 파이프라인

### 0. 상태 확인
- 인수인계 문서(`docs/STATUS.md`, 또는 AGENTS.md "프로젝트" 절에 적힌 진행 상태 문서)가 있으면 먼저 읽는다. 없으면 이 줄과 6-1단계는 건너뛴다.
- `git status`로 작업 트리를 확인한다. 커밋되지 않은 사용자 변경이 있으면 건드리지 말고 알린다.
- 새 브랜치에서 작업한다: `git switch -c agentic/<짧은-이름>`.

### 1. 라우팅 판정
```
node tools/agentic/decide.mjs route --state "<요청 원문 + 관련 파일 목록>"
```
- 출력의 `verdict`를 참고하되, `fallback: true`이거나 `uncertain`이 포함되면 네가 직접 판단한다.
- `ambiguous`가 참이면 구현 전에 AskUserQuestion으로 1~3개 질문한다.
- `size`가 large면 계획(변경 파일, 단계, 테스트)을 먼저 보여주고 승인을 받는다.
- 판정의 `council` 값은 쓰지 않는다 (설계 협의 단계 없음, 2.5단계).
- 출력의 `tier`(light·standard·deep)가 이 요청의 난이도 등급이다. 얼마나 깊이 생각해야 맞게 풀리는지를 본 값이고 변경량과는 다르다.
  `selection`은 그 등급에서 쓸 모델·추론 강도다. 이후 단계의 리뷰·리서치·서브에이전트에 이 등급을 쓴다.
- `tier`가 없거나(`fallback: true`) `tierUncertain`이 참이면 네가 직접 고른다:
  답이 하나뿐인 기계적 수정·조회는 light, 여러 부분이 맞물리거나 엣지 케이스를 따져야 하면 standard,
  미묘한 정확성·보안·동시성·데이터 무결성·구조 결정이 걸리면 deep. 애매하면 standard.
- 등급이 정해지면 위 "모델·추론 강도 고르기"의 1~3번(가용 모델 확인, 출발점, 조정)으로 단계별 모델·강도를 정해 둔다.
- 파이프라인 없이 바로 처리하는 질문·한 줄 수정에서 서브에이전트를 부를 때도 같은 기준으로 등급을 골라 쓴다 (판정은 생략해도 된다).

### 2. 리서치 (판정에서 research_needed가 참일 때만)
- 1순위: `node tools/agentic/agy-research.mjs "<조사 질문>" --tier <등급>` (모델·강도를 조정했으면 `--model <id> --effort <강도>`도 붙인다)
- 종료 코드 75(한도·출력 없음·미설치)면 `researcher` 서브에이전트에게 같은 질문을 맡긴다.
- 결과는 `.agentic/research/`에 남는다. 핵심만 요약해서 다음 단계에 쓴다.
- 화면을 새로 만들거나 레이아웃·사용자 흐름을 바꾸는 작업이면 질문 앞에
  "`<프로젝트 루트 절대 경로>/.agentic/references/ui-ux.md`를 먼저 읽고 그 조사 순서·출처·결과 형식을 따른다"를 붙인다
  (agy는 다른 폴더에서 실행되므로 상대 경로가 아니라 절대 경로로 쓴다. researcher 서브에이전트에도 같은 문장을 넘긴다).
  색·여백·문구만 바꾸는 작업에는 붙이지 않는다.
- 사실 확인이 중요한 질문(버전, 지원 여부, API 동작)은 `codex exec --sandbox read-only`에도 같은 질문을 따로 하고,
  두 답이 다른 항목은 "미확인"으로 표시한다.

### 2.5. 접근법이 갈릴 때
에이전트 간 설계 협의는 하지 않는다 (`council.mjs`를 돌리지 않는다). 네가 관리자로서 방향을 정한다.
- 접근법이 갈리면 선택지, 장단점, 추천안과 이유를 정리해 1단계 계획 승인 때 사용자에게 보인다. 새 승인 지점을 만들지 않는다.
- 사용자가 계획 승인을 이미 했다고 하면 추천안으로 진행하고, 선택한 안과 이유를 최종 보고에 적는다.
- 사실 확인이 필요하면 2단계 리서치(agy)에 조사만 맡긴다. 결정은 네가 한다.

### 3. REA 필요 여부 (다른 앱·서비스를 참고해 비슷한 기능을 만들 때만)
```
node tools/agentic/decide.mjs rea --state "<무엇을 알아야 하는지 + 대상 앱 종류>"
```
- `needs_internal`이 참이고 확신도가 기준 이상이면, 근거를 한 줄로 설명하고 사용자 승인을 받은 뒤 REA를 쓴다.
- 결과는 AGENTS.md의 클린룸 규칙대로 `docs/specs/`에 명세서로만 남기고, 구현은 새 세션에서 하도록 안내한다.

### 4. 구현
- AGENTS.md 코드 규칙을 따른다. 테스트를 먼저 또는 함께 작성한다.
- 테스트·린트·타입체크를 실제로 실행하고 통과시킨다.
- `.agentic/config.json`의 `ci.enabled`가 참이면 `node tools/agentic/ci.mjs run`으로 CI와 같은 검사를 로컬에서 돌린다.
  커밋 전에는 `node tools/agentic/ci.mjs guard`로 비밀값·`.env`가 섞이지 않았는지 확인한다.

#### 4-0. 조각을 Codex에게 맡기기 (선택)
작업이 서로 다른 파일을 고치는 독립된 조각으로 나뉘고, 조각마다 지시를 몇 문장으로 완결되게 쓸 수 있을 때만 쓴다.
설계 결정이 남은 조각, 다른 조각과 같은 파일을 고치는 조각, 고위험 영역(인증·결제·데이터 삭제·마이그레이션·인프라)은 맡기지 않고 네가 한다.
```
node tools/agentic/codex-implement.mjs --name <짧은-이름> --task "<작업 지시>" --tier <그 조각의 등급>
```
- 지시에는 목표, 고칠 파일·영역, 완료 조건(통과해야 할 테스트)을 적는다. 긴 지시는 `--task-file <파일>`로 넘긴다.
- 조각이 여럿이면 백그라운드로 함께 돌리고, 그동안 너는 네 몫을 구현한다. 방향은 네가 정하고 Codex와 협의하지 않는다.
- 종료 코드 0이면 출력의 `WORKTREE`에 커밋되지 않은 변경이 있다 (출력에 `COMMITTED=`가 있으면 Codex가 지시와 달리 커밋한 것이니 그 커밋도 같이 본다). Codex의 보고를 그대로 믿지 말고
  `git -C <WORKTREE> status --short`와 `git -C <WORKTREE> diff`, 새 파일을 직접 읽어 검토한다. 이 검토가 그 조각의 교차 리뷰다.
  범위를 벗어난 변경은 버리고, 받아들일 변경은 그 워크트리에서 커밋한 뒤 작업 브랜치로 가져온다 (`git cherry-pick <커밋>`).
- 가져온 뒤에는 `git worktree remove <WORKTREE>`와 `git branch -D <BRANCH>`로 치우고, 전체 테스트를 다시 돌린다.
- 종료 코드 75는 첫 줄로 구분한다.
  - `CODEX_UNAVAILABLE`: 돌리지 못했다. 그 조각을 직접 구현한다.
  - `CODEX_NO_CHANGE`: 돌았지만 바꾼 것이 없다. 함께 나온 Codex의 답을 읽는다. 정보가 부족하다는 답이면 지시를 보완해 다시 맡기거나,
    네가 정할 수 없는 것이면 사용자에게 묻는다 (승인 지점 1). 그 밖에는 직접 구현한다.
  - `CODEX_INCOMPLETE`: 워크트리에 끝나지 않은 변경이 남아 있다. 이어 쓸지 버릴지 네가 정하고 치운다.

### 5. 리스크 판정
```
git diff --stat <기본 브랜치>...HEAD | node tools/agentic/decide.mjs risk --state "<변경 요약>" --state-file -
```
- `verdict.needs_approval`이 참이면 (인증·결제·데이터 삭제·마이그레이션·인프라 등) 리뷰 전에 사용자에게 변경 요약을 보여주고 승인을 받는다.
  이때 6단계 리뷰는 1단계 등급과 상관없이 deep으로 받는다. 모델은 가용 목록에서 가장 강하다고 판단되는 것(같은 계열의 최신 세대, 설명이 가장 깊은 추론을 말하는 것)으로 고르고,
  판단이 서지 않으면 모델은 그대로 두고 강도를 그 모델의 `efforts` 중 `max` 이하에서 가장 높은 값으로 올린다.

### 6. 교차 리뷰
```
node tools/agentic/codex-review.mjs --tier <등급> [--model <id> --effort <강도>]
```
- `--model`·`--effort`는 "모델·추론 강도 고르기"에서 조정한 값이 있을 때만 붙인다.
- 종료 코드 75(한도 초과·미설치)면 `reviewer` 서브에이전트로 같은 리뷰를 받는다.
- 4-0단계에서 가져온 조각이 있어도 리뷰 대상은 그대로 전체 변경이다 (조각 자체는 네가 이미 검토했고, 여기서는 조각들이 맞물리는지를 본다).
- 지적 사항마다 분류한다:
  `node tools/agentic/decide.mjs review-triage --state "<지적 사항 1개>"`
- `must_fix`는 반드시 고친다. `should_fix`는 범위 안이면 고친다. `nit`과 `invalid`는 보고만 한다.
- 고친 뒤 테스트를 다시 돌린다. 리뷰-수정은 최대 2회까지만 반복하고, 그래도 남으면 사용자에게 넘긴다.

### 6-1. 인수인계 문서 확인 (인수인계 문서가 있는 프로젝트만)
```
git diff <기본 브랜치>...HEAD -- docs/STATUS.md
```
- 비어 있으면 단계 상태(확인한 날짜·방법), 기획·계획 문서에 없는 결정, 알려진 이슈, 환경 준비물을 이번 변경에 맞게 고치고 커밋한다.
- 바뀐 것이 정말 없으면 (문구 수정 등) 고치지 않고, 8단계 보고에 그 이유를 적는다.

### 7. 완료 게이트
```
node tools/agentic/decide.mjs done-gate --state "<요청 원문 + 테스트 결과 요약 + 남은 이슈>"
```
- `claim_supported`가 거짓이면 무엇이 부족한지 확인하고 보완하거나, 사용자에게 미완료로 보고한다.

### 8. 보고
- 작업 중 켠 시뮬레이터·에뮬레이터·개발 서버는 끝나기 전에 내린다. 다른 세션이 쓰고 있으면 그대로 두고 보고에 적는다.
- 무엇을 바꿨는지 3~5줄, 테스트 결과, 남은 이슈, 대체 경로를 쓴 단계를 보고한다.
  인수인계 문서가 있으면 갱신 여부(고친 절, 또는 고치지 않은 이유)를, 기기를 켰으면 내린 기기·남겨 둔 기기를 함께 적는다.
  난이도 등급과 그 등급을 누가 정했는지(판정 모델 / 직접)도 한 줄로 적는다.
  리뷰·리서치·서브에이전트에 쓴 모델·강도와 고른 이유를 단계마다 한 줄로 적는다 ("모델·추론 강도 고르기" 6번).
  Codex에게 맡긴 조각이 있으면 조각 이름, 쓴 등급, 가져온 것과 버린 것을 적는다.
- 커밋은 해도 되지만 `git push`·머지는 사용자 승인 후에만 한다.
- 이 세션의 스킬 목록에 `ship`이 있으면, 보고 끝에 한 줄로 "`/ship`을 입력하면 push·PR 생성·PR 리뷰 대응까지 진행한다"고 알린다.
  `/ship`은 사용자가 직접 입력해야 시작되므로 네가 대신 실행하지 않는다. 사용자가 입력하면 이 브랜치의 push와 PR 생성을 승인한 것으로 본다 (머지는 포함하지 않는다).
- `ci.enabled`가 거짓인데 이 저장소에 테스트 명령이 있으면, 보고 끝에 한 줄로
  "`node tools/agentic/ci.mjs suggest`로 CI 검사를 켤 수 있다"고 알린다 (켜는 것은 사용자가 정한다. 따로 묻지 않는다).

## 사람 승인 지점 (이것 외에는 묻지 말고 진행)
1. 요구사항이 모호할 때 (1단계)
2. 큰 작업의 계획 (1단계, 접근법이 갈리면 선택지와 추천안 포함)
3. REA 사용 (3단계)
4. 고위험 변경 (5단계)
5. push·머지·배포 (사용자가 `/ship`을 입력했으면 그 브랜치의 push·PR 생성은 승인된 것이다. 배포는 `node tools/agentic/cd.mjs plan` 출력을 보여 주고 승인을 받은 뒤 `cd.mjs deploy --yes`)
6. 외부 CLI 업데이트 (사용자 설정 `cli-update.json`의 `auto`가 참이 아닐 때. "CLI 업데이트" 절)
